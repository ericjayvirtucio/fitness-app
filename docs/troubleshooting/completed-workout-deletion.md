# Completed workout deletion troubleshooting

| Symptom                                                    | Likely cause and diagnostics                                                                      | Resolution                                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| An active workout was deleted through completed history    | `discard` was widened, or the completed status was not checked.                                   | `deleteCompleted` refuses anything that is not completed, in the use case and again in the repository.            |
| Completed deletion appears on the active workout screen    | The active screen reached the history use cases.                                                  | Deletion lives only in `workout-history`; the active screen keeps `discard` and nothing else.                     |
| A workout disappeared without anybody deleting it          | Something other than the deletion path removed rows.                                              | No catalog edit, plan change, preference, migration, or background task may write here; find the other writer.    |
| Orphaned `workout_set` rows appear                         | The children were left to `ON DELETE CASCADE` inside the transaction, where foreign keys are off. | Delete sets, then exercises, then the session, explicitly; assert the orphan count in a test.                     |
| Orphaned rows appear only after the parent is gone         | The orphan check joined back to a session that no longer exists.                                  | Hold the owned exercise identifiers before deleting anything and verify against them.                             |
| A failed deletion left half a workout                      | Writes ran outside the exclusive transaction.                                                     | One `runExclusive` per deletion; a throw must roll the whole thing back.                                          |
| Deletion reported success but rows remain                  | The verification step was skipped or its result ignored.                                          | A surviving parent, exercise, or set must throw before the transaction commits.                                   |
| Another workout changed                                    | A statement was not bound to the selected session.                                                | Every statement takes the session identifier; assert the other workout row-for-row in a test.                     |
| An old screen deleted a newer workout                      | The loaded lifecycle instants were not compared against storage.                                  | Send the loaded start and completion instants and refuse as `changed` when they no longer match.                  |
| Deleting twice raised an error                             | The second attempt was treated as a failure rather than as nothing to do.                         | An already-missing workout is a refusal that reads as no longer available; keep the control disabled in flight.   |
| Back reopened a deleted workout                            | The post-delete navigation pushed instead of replacing.                                           | Replace the detail route with Workout History so the deleted route leaves the stack.                              |
| History still lists the deleted workout                    | The list was not reloaded, or a page was cached.                                                  | History reloads on focus and is derived; never persist a list or a summary.                                       |
| A personal record still points at the deleted workout      | Something derived was cached or persisted.                                                        | Nothing derived is stored; reopen the screen so the reader recomputes from the remaining history.                 |
| Progress totals did not follow a deletion                  | A screen did not reload, or a summary was persisted.                                              | Progress reloads on focus and is derived; never persist a summary.                                                |
| The completed workout count did not change                 | The parent row survived the deletion.                                                             | The count comes from parent rows; verify the parent is gone before committing.                                    |
| A deleted workout is still in a new export                 | The export ran against a stale read or a cached page.                                             | Export reads current rows; recreate the export after the deletion commits.                                        |
| A restored export brought the workout back                 | That file was created before the deletion.                                                        | Expected. Deletion changes local data only and never reaches a saved file; say so rather than implying otherwise. |
| The Exercise Library lost or regained a definition         | The deletion touched catalog rows.                                                                | Deletion is confined to the session aggregate; history reads snapshots and recreates nothing.                     |
| A failure message names a workout, a value, or a date      | An error was built from data rather than from the refusal reason.                                 | Map each refusal to its fixed sentence in `completed-workout-deletion-messages.ts`.                               |
| The interface offers undo or recovery                      | Wording was added without any stored copy.                                                        | No undo, trash, audit, or tombstone exists; remove the claim rather than inventing the data.                      |
| Deletion is reachable by swiping a history card            | A gesture was added without a proportionate confirmation.                                         | Deletion starts on the completed detail and always passes through the destructive alert.                          |
| The Maestro alert tap hits the title instead of the button | The title and the destructive action share their words.                                           | Tap the exact button text and let full-match semantics separate it from the title.                                |
